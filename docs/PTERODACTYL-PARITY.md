# Паритет с Pterodactyl

Что из функционала Pterodactyl перенесено в OmniDash, что сделано иначе и чего пока нет.
Документ — карта решения, а не реклама: ограничения перечислены явно.

## Концепции

| Pterodactyl | OmniDash | Комментарий |
|---|---|---|
| Panel (PHP/Laravel) | один Node.js-процесс + JSON-база | без Composer, без миграций, запуск одной командой |
| Wings (демон на ноде) | `core/daemon.js` в том же процессе | процессы ОС, статистика через `ps`/`/proc`, без контейнеров |
| Egg | шаблон (`core/eggs.js`) | `startup`, env-переменные, конфиг-файлы, иконка и цвет |
| Allocation | аллокация (`ip:port` на узле) | диапазоны, массовое создание, основной порт |
| Nest | категория шаблона | поле `category` |
| Subuser | субпользователь | 9 независимых прав, выдача владельцем или админом |
| Server | сервер | владелец, узел, шаблон, лимиты, срок, порты |
| Node | узел | логическая запись: локация, FQDN, диапазон портов, лимиты |
| API key | `od_…` ключ | Bearer-авторизация |
| Tasks | расписание | интервал / ежедневно / еженедельно / cron-подобно |
| Backups | ZIP-бэкапы | создание, восстановление, скачивание, лимит |
| Audit log | журнал | действия людей и системы |

## Отличия в архитектуре

| Аспект | Pterodactyl | OmniDash |
|---|---|---|
| Язык | PHP (Laravel) + Go (Wings) | JavaScript (Node.js), без зависимостей |
| Изоляция | Docker + cgroups | процессы ОС, без изоляции |
| Ноды | распределённые | один процесс, узлы логические |
| Хранилище | MySQL/MariaDB | JSON-файл |
| Фронтенд | React-сборка | ES-модули без сборки, hash-роутинг |
| Реальное время | WebSocket | SSE |
| Установка | composer, артизан, Wings, SSL | `node server.js` |
| Обновление | git pull + миграции | ZIP-пакет + бэкап кода |

## Когда выбирать OmniDash

- Нужна лёгкая панель для своей машины или небольшой команды.
- Хочется «как Pterodactyl», но без Docker, MySQL и двух сервисов.
- Нужны выдача доступов, порты, лимиты и сроки без биллинга.
- Важна возможность быстро менять интерфейс и смотреть результат вживую.

## Когда Pterodactyl остаётся лучше

- Публичный хостинг с недоверенными пользователями и изоляцией.
- Много нод, миграции, SFTP на каждую ноду.
- Готовые яйца из каталога сообщества и интеграции (биллинг, WHMCS).
- Требования к 2FA, OAuth, аудиту корпоративного уровня.

## План миграции

1. Сменить демо-данные: пароли, пользователи, узлы.
2. Создать узлы и аллокации, затем шаблоны (startup + переменные).
3. Завести пользователей и лимиты, выдать серверы.
4. Перенести файлы серверов в `data/servers/<id>/`.
5. Настроить сроки и расписание бэкапов.
6. Подключить HTTPS-прокси и закрыть порт панели.
